# 固定主机航线下的 AI / NPU 规划与工程整改

> 2026-10-21：实机方向已从三架无人机改为 **1 架固定航线主机 + 2 台地面中继小车**；下文“两架中继/三机”是 P0 relay-drone 历史设计记录，当前新车配置见 [单主机两小车架构](单主机两小车架构_20261021.md)。

> 2026-10-21：下文为原整改设计记录；格长、停留、逐格遮挡、拓扑、时间戳、移动就位、观测有效性和两条规则基线现已实现并测试。当前规范与剩余限制以 [ABC统一契约与验收](ABC统一契约与验收.md) 为准，旧版差异表不再描述当前默认代码。

更新：2026-10-12。设计修订后已将 B 主机仿真及 SITL 任务生成的去程同步为总 README 的竖列蛇形路线；未实现新模型、组网或飞控改动。路线修改验证见 [B 验证记录](../swarm_cooperation/swarm_cooperation/VALIDATION.md)。

后续进展：B已增加独立的五轮理想算法实验（1m/格、随机/手动窗口移箱、局部地图观测、第二轮起候选调度及AI评分接口），详见 [IDEAL_SIM.md](../swarm_cooperation/swarm_cooperation/IDEAL_SIM.md)。下文涉及原B参数与物理闭环缺口的内容仍指 `--legacy` 骨架；理想实验不代表真实组网、动力学或NPU已经实现。

## 1. 已确定的边界

用户确认：主机伴飞电脑 Orange Pi 5 Plus，D435 用于主机定位；各节点使用 Wi-Fi 网卡，按已经能双向通信规划，中继定位未定。**本轮不展开网卡选型、视觉算法或多模态融合，集中在 RSSI 预测与中继调度。**

主机路线固定，中继路线和动作需要调度。位置、路线进度及就位状态是调度输入；D435 如何产生主机位姿由机载定位模块负责，不新增 NPU 视觉任务。

项目主问题可表述为：

> 在已知主机巡检路线、只能获得当前及历史通信观测的条件下，提前部署两架中继，选择可行通信路径，并在减少断链的同时控制移动、切换和占用代价。

不把“网卡能互通”混同为“中继任务已经执行成功”：软件仍需接收任务、报告到位、提交并确认路径。这些作为通信适配接口保留。

## 2. 现有能力与缺口

| 层次 | 已有实现 | 缺口 |
|---|---|---|
| 主机轨迹 | A/B/C 已采用相同竖列蛇形去程及末尾补飞；V3 统一为1m/格 | V3 已统一格长、停留和进度；旧B的2m/格仅存档 |
| 链路模型 | V3 统一为逐格遮挡、五种路径取最弱跳、无固定增益 | 历史 A/C 的固定中继+6dB 已作废，不可合并结果 |
| 预测 | C 的 25→64→32→1 MLP，预测未来 1.5s 直连低于 -75dBm | 不预测中继到位时间，不输出中继位置或任务 |
| 动作 | C 选择 direct/relay1/relay2，默认建立延迟 0.5s | 中继预先就位，不含部署运动和路由依赖 |
| 协同 | B 有主机/中继状态机、握手字段与 SITL 接口骨架 | 未接入 C 预测，未实现三机闭环 |
| 板端 | 有 ONNX、校准数据和 PC 报告 | 无 Icraft 实板结果，无 PL 特征 IP 与完整数据流 |

当前证据支持“弱链路预测辅助链路选择”，不支持“已完成 AI 中继机自主调度”。后续工作的价值应放在补齐这段差距。

## 3. 固定航线应该怎样用于预测

### 3.1 用路线进度消除运动方向歧义

主机在去程和返程可能经过同一个坐标，且标量速度相同，但接下来走向不同。现有 x/y/speed 特征不能完整表达这种差异。

建议维护以下输入契约：

| 输入组 | 内容 | 来源 |
|---|---|---|
| 路线定义 | route_id、路线版本、合法航段、停留点 | 已知任务配置 |
| 当前进度 | segment_id、phase、沿路距离 s、实际速度、当前停留状态 | 机载状态与位置 |
| 链路历史 | 每个有向物理跳的 RSSI 窗口、测量年龄、有效位 | 网卡测量/通信适配器 |
| 中继状态 | 位置、移动目标、ready、预计到位时间、当前任务、电量 | 中继反馈 |
| 已知未来 | 按路线与当前速度/任务计划估计的未来主机位置 | 在线确定性外推 |

路线本身允许用于预测，它在任务开始前已知。不能使用未来真实 RSSI、未来实际速度、未发生的故障等信息。“计划位置”与“后来真实到达的位置”要分开存储。

### 3.2 从直连预测扩展到物理跳预测

需要考虑的链路至少包括：

- 地面 ↔ 主机；
- 地面 ↔ R1、地面 ↔ R2；
- R1 ↔ 主机、R2 ↔ 主机；
- 双机串联时的 R1 ↔ R2。

上下行分别测量或明确近似对称假设。可以先用共享的小型 MLP 对每个链路/候选时刻分别推理，再依据 Icraft 算子支持和实测延迟决定是否合批。小模型放到 NPU 不自动意味着比 CPU 更快。

第一版扩展建议仍预测“未来窗口内弱链路概率”，便于与现有二分类基线对照；如需要精确比较候选，再增加多个时刻的 RSSI 回归输出或保守分位预测。回归与分类的校准、损失和指标分别报告。

候选站位如果没有实际 RSSI 历史，其预测属于位置条件下的外推，必须带缺测标志并用相应数据训练，不能把当前站位的历史伪装成候选点实测。不能给不同链路填同一窗口，也不能把断线后的最后一个良好值无限沿用。

### 3.3 区分两种时域

| 时域 | 解决的问题 | 决定方式 |
|---|---|---|
| 切换时域 | 已就位中继何时接管 | 测量处理 + 推理 + 路由建立/确认 + 余量 |
| 部署时域 | 中继何时起飞并前往站位 | 起飞 + 飞行 + 稳定就位 + 链路建立/确认 + 余量 |

以历史 B 的 R1 到 (1,2)、2m/格、2m/s 为例，起飞 2s 加移动约 3s 已超过当时 1.5s 窗口。当前 V3 为 1m/格，实际值应来自测量与 mission_profile；该计算只保留为历史示例。

首期可预先部署中继，用短时模型完成切换闭环；随后利用已知航线建立较长时域部署预测。不能未经训练就让 1.5s 模型承担 5s 或更长的预测任务。

若预测有效时域短于部署时间，使用按航段预部署的保守规则；不能等待模型报警后才从待命起飞。主机可按任务策略等待中继就位，但不擅自改变固定航线。

## 4. 调度设计：先可验证，再学习评分

### 4.1 阶段一：NPU 预测 + CPU 有限候选规划

首期保留有限站位集合，不直接生成连续飞行轨迹。CPU 在每个规划周期根据中继当前状态生成动作：

| 动作 | 参数与检查 |
|---|---|
| HOLD | 维持当前站位和必要转发职责 |
| MOVE | 目标候选站位、允许航段、出发时刻；检查到位时间及电量 |
| ACTIVATE | 目标通信路径；检查全路径与节点就位 |
| HANDOVER | 新旧路径、route_epoch；新路径确认后才释放旧路径 |
| RETURN | 返场路径；检查是否仍被下游依赖 |

主机路线不变，中继自身也只能沿允许路线飞行。已经起飞或移动中的中继不能被当成瞬时到位，候选计划需要包含过渡期的链路质量。

硬约束先筛选：到位不晚于需求时刻、定位状态有效、电量足够、航段不冲突、任务/路由版本一致、上下游可达。暂时不可行的计划不会因模型评分高而获选。

可采用分层排序：先按预测断链风险，再按不可覆盖时长、切换次数、移动距离/能耗和占用时间排序；如果改用加权代价，各项先归一化，权重只在训练/验证场景选择，不能用最终测试集调优。

### 4.2 如何组合多跳预测

路径包含的任意一跳不可用，端到端业务就可能中断。预测 RSSI 的“最弱跳”只能作为链路强度代理，不代表真实端到端吞吐。

若输出各跳事件概率 p_e，可以用 min(1, Σp_e) 作为同一时间窗口内“至少一跳出问题”的联合概率上界。各跳概率须有校准依据；不假定独立就不能直接把概率乘积当作精确路径可靠度。

最终断链结果仍应根据业务心跳/数据到达等实测定义判断；-88dBm 是现有仿真阈值，不是所有网卡通用的断链值。

### 4.3 阶段二：可选 NPU 候选计划评分网络

如果希望 NPU 同时承担预测和调度评估，可增加轻量评分模型：

~~~text
当前链路/路线/中继状态 + 候选计划
                  ↓
           NPU 调度评分网络
                  ↓
    预计断链风险、完成代价或候选分数
                  ↓
       CPU 选择可行计划并执行握手
~~~

模型不直接输出电机控制，也不替代硬约束。输入需要对站位、动作、到位时间与路由编码，固定维度和归一化必须写进模型版本。

训练标签由离线仿真搜索/滚动规划产生。离线使用后续环境评估一个候选的真实代价可以用于造标签，但部署输入不得含未来观测。专家规划器和评分网络要用独立场景比较；不能只报告模型拟合专家标签的准确率。

对于只有两架中继和少量站位的系统，CPU 枚举可能已经足够便宜。保留第二模型的条件应是可测量收益，例如候选规模增加时减少规划时间，或在同样候选预算下改善结果。竞赛只要求至少一种 AI 模型，不必为数量重复部署两个作用相同的模型。

## 5. FPGA 与 NPU 的可交付职责

### 5.1 最小 RSSI 特征 IP

建议从明确的流式接口开始：

~~~text
PS 接收测量记录
{link_id, seq, local_sample_time, rssi, valid}
    → DMA 输入队列
    → PL 按链路缓存定长窗口、标记缺失、定点缩放/打包
    → DMA 输出特征与有效位
    → CPU 补路线/中继状态字段
    → NPU 推理
~~~

PS 负责把远端时钟/年龄转换为可比较的时间语义。PL 不直接用互不校准的机载时间戳判断数据先后。

首个 IP 可以只实现窗口缓存和打包；数据清洗/滤波如果以后加入，会改变模型输入分布，必须同步更新训练与软件参考。现有模型直接使用 RSSI 历史，不能擅自在部署端加平滑后沿用旧精度结论。

验证重点：乱序、丢样、重复、窗口不足、固定点溢出、复位、DMA 背压和多链路交错；输出与 CPU 参考逐项对齐。窗口填充规则不得把未来样本放回过去。

目前仅数条链路、约 10Hz 的数据量很小，应如实测量硬件收益；报告 IP 核心延迟、完整 DMA 开销、资源与 CPU 占用，不预设一定加速。Lite PL 千兆网口未焊接，网卡测量经 PS 进入内存，见 [赛题指南](../de2aca5a-535d-4288-aecd-aed3d0cf5841.pdf) 第 4～5 页。

### 5.2 NPU 上板验证

1. 先部署现有固定输入 [1,25] 的 MLP，确认 Icraft 解析、量化、编译、运行和输出阈值一致。
2. 训练集代表样本用于校准；测试集不参与量化阈值/模型选择。
3. 扩展路线与多跳输入后发布新版本，重新生成数据、训练、导出和校准，不复用旧权重或旧结果报告。
4. 分别测输入准备、传输、NPU 执行、输出后处理和整轮调度的均值及 p95/p99。
5. NPU 超时、不可用或输入失效时，CPU 进入规则回退，不阻塞通信与机载控制。

现有 ORT 动态 INT8 ONNX 是 PC 产物，不能直接视作 Icraft 可执行模型。Orange Pi 的算力用于机载任务，不能替代赛题要求的 FMQL30TAI 模型部署。

## 6. 数据与实验必须随任务升级

当前数据集中的中继固定，不能训练或证明“中继运动调度”效果。新版仿真至少增加：

- 中继起飞、移动、稳定就位及返场过程；
- 实际路线进度偏差、主机速度扰动和停留；
- 各跳遮挡、相关噪声、测量丢失、时延与过期；
- 链路建立时间分布、失败重试、路由交接与节点故障；
- 中继站位候选、占用、移动距离和路由依赖。

对同一环境/动作历史保持可复现。移动中继会改变物理链路，旧“所有策略复用完全相同的 links 数组”方法不再适用。应共享外部扰动场/种子，用每种策略的实际节点位置计算链路；不得给不同策略随意抽取不同天气/遮挡条件，也不得强行让不同位置得到同一个 RSSI。

| 组别 | 作用 |
|---|---|
| 被动门限规则 | 直连变弱后响应，建立基本对照 |
| 已知航线的预部署规则 | 利用固定任务提前安排，防止 AI 只胜过过弱基线 |
| NPU 预测 + CPU 规划 | 测模型对动态噪声/速度变化的实际收益 |
| 预测 + NPU 评分（可选） | 测第二模型是否改善时延或决策质量 |

按完整航程、遮挡条件和采集批次划分训练/验证/测试；增加未见干扰强度、速度、停留和站位组合的测试。固定路线只说明路线内适用性，不能外推为任意仓库泛化。

主要指标：断链次数/时长、最长连续中断、提前量分布、到位成功率、任务完成率、切换/乒乓次数、移动距离/能耗代理、中继占用率、推理与调度 p95/p99。召回率必须对应明确标签，不能把 -75dBm 弱链路召回率写作真实断链预测准确率。

## 7. 稳定性整改顺序

| 优先级 | 工作 | 验收 |
|---|---|---|
| P0 | 统一 A/B/C 路线、单位、拓扑和时间契约 | 同一轨迹的距离/遮挡/链路含义一致 |
| P0 | 中继移动状态与到位时间建模 | 移动期间不能假就位，已有链路不被提前释放 |
| P0 | 观测有效性与失联入口 | 缺测/过期/NaN 不当作良好信号；无可行路径时可降级 |
| P1 | 路线条件下的多跳预测及预部署规则 | 测试不读取未来观测，能和强规则基线比较 |
| P1 | 有限候选规划与事务握手 | 重复命令幂等，旧 ACK 无效，新路径失败时不误提交 |
| P1 | PL 特征 IP 与 Icraft 单模型闭环 | 数值对齐，报告完整耗时、资源和失败回退 |
| P2 | 可选调度评分网络 | 相对预测 + CPU 规划有可量化收益 |
| P2 | 实测标定与三机闭环 | 真实链路、定位、执行确认可追踪，故障可重复 |

交接流程为“准备 → 实际到位 → 双向业务探测 → 提交 → 执行确认 → 释放旧链路”。链式 R1→R2 中，R1 在 R2 仍依赖它时不能返场。最短驻留和持续恢复计时抑制乒乓，但当前路径失效时要允许紧急处理。

机载保存主机路径及失联执行逻辑；定位失效与通信失效分开处理。原生 ArduPilot GCS failsafe 监测地面心跳超时，恢复心跳不会自动恢复先前模式，需与应用恢复策略协调。[官方 GCS failsafe 文档](https://ardupilot.org/copter/docs/gcs-failsafe.html)
