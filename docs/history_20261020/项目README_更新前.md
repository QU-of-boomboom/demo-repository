# 仓库无人机 RSSI 预测与中继调度系统

> 全国大学生嵌入式芯片与系统设计竞赛 2026 · FPGA 创新设计赛道（复旦微电子）
> FMQL30TAI-悟净 lite：FPGA 链路数据预处理 + NPU 链路预测/调度评分 + CPU 协同控制

## 1. 项目定位与范围

主机沿**预先确定的仓库巡检航线**飞行。当货架遮挡使通信质量下降时，系统利用 RSSI 历史、主机航线进度和中继状态，提前安排两架中继机就位、接力及返场，维持主机到地面站的通信。

**AI 主线是 RSSI 预测和中继机调度，不开展视觉识别、货物检测或视觉多模态融合。** 主机路线不由 AI 生成；AI 主要解决“何时需要中继、哪架中继前出、去哪个候选站位、何时切换及交接”。

| 节点 | 用户已确认的组成与方向 |
|---|---|
| 地面站 | FMQL30TAI-悟净 lite + Wi-Fi 网卡，承担预测、调度和状态展示 |
| 主机 | MicoAir743v2 + Orange Pi 5 Plus + D435 + Wi-Fi 网卡；执行固定航线，D435 用于机载定位方向 |
| 中继机 ×2 | MicoAir743v2 + 网卡通信节点，执行就位、接力、返场；定位方案未定 |
| 通信 | 全部采用 Wi-Fi 网卡，取消原独立路由器和 ESP32 透传方案；本轮按节点间可双向通信规划 |

网卡选型与组网细节不在本轮范围。调度层只要求通信适配器提供：相邻链路测量、任务发送、到位状态、转发路径提交与确认。主机视觉定位作为独立基础能力推进，不纳入本轮 NPU 功能规划。

当前交付是三个独立的 PC 仿真/协议原型，尚未完成统一调度器、三机实飞和板端闭环。详细设计见 [AI 与 NPU 作用规划及整改清单](docs/工程可行性与整改清单.md)。

## 2. 场景与必须统一的约定

- 地图横 3、竖 4 个货架格子，格线为航线；起点 (0,0)，终点 (3,4)。
- A/B/C 当前去程：(0,0) → (0,4) → (1,4) → (1,0) → (2,0) → (2,4) → (3,4) → (3,0) → (3,4)。返程按实际去程严格逆序。
- 末尾补飞 4m，是 A/C 为覆盖四条竖格线且保留终点采用的约定；1m/格时单程 23m。A 含终点停留共 47s，C 标称不含停留共 46s。
- B 默认升级为理想算法实验：1m/格，5个完整往返、10个单程、主机总航程230m；首次巡线前建立20节点/31航段，首轮返程支持随机或手动窗口移除2–4块货箱，第二轮起按更新地图规划中继。旧版 `--legacy` 及飞控SITL骨架仍为2m/格、停留3s。链路模型和任务流程未与A/C完全统一，各模块结果仍不能混作同一系统验证。
- 现有中继站位 (1,2)、(2,4) 首期作为离散候选；移动仅沿允许航段。固定主机航线不等于时间表固定，实际速度、停留和到达进度仍需观测。
- 旧原型中的取货保留为任务停留事件，不是本轮 AI 目标，也不以计时器结果宣称真实抓取成功。

建议先统一路线、格长、候选站位、速度、停留、链路拓扑和时间戳语义，再接入预测与调度。真实场地尺寸需根据机体和定位误差确定。

## 3. CPU / NPU / FPGA 分工

| 单元 | 本项目职责 | 输出与边界 |
|---|---|---|
| FPGA（PL） | RSSI 记录整理、窗口缓存、有效性标志、定点缩放和特征打包；首期选其中一项实现 IP | 输出模型输入；RSSI 来自网卡驱动，不是 PL 直接采集射频 IQ |
| NPU | 首期部署弱链路 MLP；下一步结合固定航线预测各物理跳未来风险；可进一步加入候选调度评分网络 | 输出风险/链路预测及候选评分，不直接控制飞行姿态 |
| CPU（PS） | 新鲜度校验、路线进度管理、候选生成、约束筛选、计划选择、命令握手与显示 | 输出中继任务/路由版本，以实际到位和执行确认推进状态机 |
| 机载主控/飞控 | 主机固定路线执行、中继移动、本地定位与失联处置 | 地面不可达时保留本地执行与降级能力 |

首期 CPU 枚举有限候选，使用 NPU 预测结果选择可行计划。若需要让 NPU 进一步承担调度决策，可训练“状态 + 候选计划 → 计划代价”的评分模型。**现有 MLP 还不是中继动作策略网络。**

PL 数据由 PS 接收后经内存/DMA 输入。当前采样量较小，应实测 CPU 对照、PL 数值误差、资源与端到端开销，不预先宣称硬件加速。Lite 的 PL 千兆网口未焊接，见 [赛题指南](de2aca5a-535d-4288-aecd-aed3d0cf5841.pdf) 第 4～5 页。

~~~mermaid
flowchart LR
    R["各跳 RSSI / 丢包 / 测量年龄"] --> C["PS 接收与时间整理"]
    P["固定主机航线与实时进度<br/>中继位置 / 就位 / 电量"] --> C
    C --> F["PL 窗口缓存与特征打包"]
    F --> N["NPU 未来链路预测"]
    N --> S["CPU 候选生成与约束筛选"]
    S --> D["CPU 选择 / 准备 / 提交"]
    S -. 后续可选 .-> Q["NPU 候选计划评分"]
    Q -.-> D
    D --> U["中继执行与路径切换"]
    U --> R
    U --> V["到位与路由确认"]
    V --> S
~~~

## 4. AI 的两层作用

### 4.1 预测：何时、哪一跳可能不可用

现有输入为 25 维：20 点直连 RSSI 历史、主机 x/y、标量速度、到两中继的距离。标签是未来 1.5s 内是否出现 **直连 RSSI < -75dBm**；断链统计门限另为 **-88dBm**。预测窗口不是保证的提前量。

下一版利用路线已知条件加入：航段编号、去/返程方向、沿路线进度、预计未来位置、中继实际位置和就位状态。已知规划路线可以输入模型；未来真实 RSSI 和尚未观测的真实速度不能用于在线决策。

调度应覆盖地面—主机、地面—R1/R2、R1/R2—主机，以及链式接力时的 R1—R2。最后一跳强不等于整条路径可用；缺测和过期必须显式表示。

预测时域分两类：短时风险用于已就位中继切换；较长时域用于起飞/移动部署，长度按实际到位时间设定。现有 1.5s 窗口不能直接覆盖中继起飞和前出全过程。

### 4.2 调度：谁、何时、去哪里、怎样交接

首期限定动作集合：保持、移动到合法候选站位、接入可行路由、交接、返场。CPU 检查到位时间、电量、路由依赖和航段冲突，结合 NPU 预测选择计划。

目标优先级：**减少断链 → 避免来不及到位和路由断层 → 减少无效切换 → 减少移动距离与中继占用**。链式接力时，上游中继仍承担骨干职责，不能因主机不再直接连接它就返场。

后续可选调度评分网络：输入当前状态与候选计划，预测断链风险及代价；标签由离线仿真搜索产生。CPU 保留硬约束检查和失败回退。此模型尚未实现，应与“预测 + CPU 枚举”比较收益后决定是否保留。

### A：PC 巡检仿真

- 路损模型：RSSI = -40 - 22·log10(max(d,1m)) - 12 × 穿越货架列数。
- 触发 -75dBm、断链 -88dBm、回差 3dB；固定中继两跳最弱值额外加 6dB，为模型假设，不是转发必然获得的增益。
- 既有结果：46m/47s、6 次切换、最低有效 RSSI -74.88dBm、无断链、取货事件 3 个。实际均由 R1 接管，R2 为备用候选，此结果不证明双机接力。
- 进入模块目录运行 python warehouse_relay_sim.py。本轮默认环境 12 项单元测试通过。

### B：五轮理想调度与协同骨架

- 新入口：`python demo.py --mode random`；手动窗口：`python demo.py --mode window --interactive`。窗口内提交一次2–4块移除任务，首轮返程局部观测更新地图；第二轮起从20个格点枚举421种中继分配。
- 新版使用有限速度理想运动学、即时多跳探测和路由切换。`ideal_sim/scheduler.py` 保留AI评分接口，当前为CPU枚举基线；输出逐步轨迹、决策候选、同场景对照和HTML交互回放。
- [五轮实验说明](swarm_cooperation/swarm_cooperation/IDEAL_SIM.md)；[Ubuntu 22.04 + ROS 2 Humble + Gazebo Fortress 路径](swarm_cooperation/swarm_cooperation/ROS2_GAZEBO.md)。ROS包和世界已提供，尚未在Ubuntu实启验证。
- 本轮32项测试，30项通过、2项因缺少pymavlink跳过。随机与窗口脚本场景均完成5轮、230m，当前示例全阶段断链0s；此为理想仿真结果。

以下为保留的 `--legacy` 单轮状态机及协议：

- 主机：IDLE → TAKEOFF → SNAKE_SURVEY → PICK → RETURN → LAND。检测断链立即进 FAILSAFE，保持 5s，未恢复则锁定应急原路返航。
- 中继：STANDBY → HOVER → RELAYING → HANDOVER → RETURN，模拟链式依赖及返场顺序。
- protocol/swarm.xml 定义自定义消息；协议 ACK 不表示飞机到位或转发路径已可用。
- 旧版去程路线修改后演示：15次状态迁移、0次FAILSAFE、总模拟时长125.8s；旧横行路线的23次迁移记录仅作历史参考。
- sitl_bridge.py 仍为骨架，未完成三机闭环；生成方言不会使未修改的原生飞控自动执行业务命令。

### C：PC 弱链路预测与链路选择

- 5000 个仿真航程、约 224 万样本；MLP 3,777 参数。
- 既有 ORT 动态 INT8 ONNX 为 8.43KiB，弱链路标签召回率 99.15%，不直接输出中继位置/动作。
- 200 配对航程、建立延迟 0.5s、中继预先就位时：规则断链 20 次，AI 0 次；切换降 24.91%，单侧配对符号检验 p≈3e-5。
- 零延迟对照两组断链均为 0；AI 中继占用率从规则组 47.76% 增至 53.63%。收益依赖现有条件。
- model_fp32_batch1.onnx 与 icraft_calibration_inputs.npy 是 Icraft 导入/校准候选；ORT INT8 文件不是 NPU 可执行编译产物。
- 数字引用 [2026-10-06 既有报告](ai_relay_scheduler/ai_relay_scheduler/outputs/RESULTS.md)。本轮默认 Python 缺少 NumPy，原 .venv 依赖的 D:\anaconda3 已不存在，未重训或重做量化。

## 6. 不稳定工程点

| 环节 | 修改方向 |
|---|---|
| 航线与时间 | 统一三模块；根据真实进度估计未来位置，不只按计时器推算 |
| 中继准备 | 区分起飞、移动、稳定就位、路径建立，只有到位且完整链路可用才提交 |
| 输入缺测 | 每跳附方向/时间/质量；无效、缺测、过期不当作良好信号，也不假设所有候选随时可测 |
| 预测窗口 | 区分切换与部署时域；超出可靠时域时采用预部署或规则回退 |
| 抖动 | 评估回差、最短驻留和持续恢复计时；当前链路失效时不能被驻留条件锁住 |
| 路由交接 | 准备 → 到位 → 双向探测 → 提交 → 确认 → 释放旧路径；带版本、超时及幂等 |
| 机载失联 | 历史路线和执行器留在机载；区分通信失效与定位失效，不保证定位失效后仍能原路返航 |
| NPU 故障 | 超时/失败/输入无效时退回规则，不能阻塞心跳和机载执行 |
| 模型迁移 | 路线特征、移动中继、拓扑或时域变化后重新生成数据、训练及校准 |

应用失联逻辑需与 [ArduPilot GCS failsafe](https://ardupilot.org/copter/docs/gcs-failsafe.html) 协调：其以地面心跳超时触发，恢复心跳不会自动恢复原飞行模式。
